---
title: MCP tools
description: Reference for the MCP tools exposed by Lific.
---

Lific exposes 31 MCP tools. Required parameters use non-optional input fields. Optional parameters can be omitted.

A parameter a tool does not declare is refused rather than ignored, so a misspelling cannot quietly change the answer. The error is `-32602 Invalid params`, names the unknown key and suggests the closest valid parameter, for example ``Unknown parameter `comments` in get_issue. Did you mean `include_comments`?``. The same applies inside nested objects such as plan steps.

When MCP is reached over HTTP and its origin is known, issue, project, page, plan, module, and comment references are rendered as Markdown links to their canonical web routes. Comment links include an anchor that scrolls the issue or page thread to that comment. Configure `server.public_url` for deployments behind a proxy; otherwise a direct HTTP `Host` is used only when it matches the configured allowlist. Stdio MCP and direct SQL have no authoritative external hostname, so they keep plain references.

Module, label and folder names are matched as sent first. If nothing matches, a name that a client HTML-escaped (`Infra &amp; Ops`) is tried again with `&amp;`, `&lt;`, `&gt;`, `&quot;`, `&#39;` and `&#x27;` decoded, so a name that really contains one of those sequences still matches itself.

## Issues

### `list_issues`

Lists issues in a project with filters and paging.

| Name | Type | Required | Description |
| --- | --- | --- | --- |
| `project` | `string` | Yes | Project identifier (e.g. LIF) |
| `status` | `string` | No | Filter by status: backlog, todo, active, done, cancelled |
| `priority` | `string` | No | Filter by priority: urgent, high, medium, low, none |
| `module` | `string` | No | Filter by module name |
| `label` | `string` | No | Filter by label name |
| `workable` | `boolean` | No | Only return issues with no unresolved blockers |
| `blocked` | `boolean` | No | Only return issues with at least one unresolved blocker (inverse of workable). Each result lists its blockers as blocked_by:LIF-3,LIF-7. |
| `created_since` | `string` | No | Only issues created at/after this ISO date or datetime (e.g. 2026-06-01) |
| `created_until` | `string` | No | Only issues created before this ISO date or datetime (exclusive) |
| `updated_since` | `string` | No | Only issues updated at/after this ISO date or datetime. Handy for "what changed recently". |
| `updated_until` | `string` | No | Only issues updated before this ISO date or datetime (exclusive) |
| `order_by` | `string` | No | Sort column: sort_order (default), sequence, created, updated, or priority |
| `order` | `string` | No | Sort direction: asc (default) or desc |
| `limit` | `integer` | No | Max results (default 50) |
| `offset` | `integer` | No | Zero-indexed offset for paging. The output appends a hint like "has_more: use offset=N" when more results exist. |

An issue whose description contains a markdown task list ends its line with its progress, for example `checklist: 2/5`. Issues without task items carry no marker.

### `get_issue`

Gets an issue and its details.

| Name | Type | Required | Description |
| --- | --- | --- | --- |
| `identifier` | `string` | Yes | Issue identifier like PRO-42 or ADA-7 |
| `include_comments` | `string` | No | Comment trail: `recent` (default, last 3), `all` (most recent 500), or `none` (count only). |

Relation lines include the related issue's current status, for example `Blocked by: LIF-42 (done)`.

When the description contains a markdown task list, a `Checklist: 3/5 done` line follows the status and labels. Task items are `- [ ]`, `- [x]` (either case of `x`), with `*`, `+` or numbered list markers too, nested or not. Items inside fenced code blocks are not counted, so a task list quoted as an example does not become the issue's checklist.

The comment trail is bounded in every mode, and each mode reads only the rows it renders. `none` loads no comment bodies at all and reports the total. `recent` loads three. `all` loads the most recent 500, the same cap every other comment list uses, and is not a way to retrieve an entire thread: when a thread is longer than that, the header says it is showing the most recent 500 and directs you to `list_comments` for the rest. Every mode prints its comments oldest first.

### `export`

Exports as Markdown, dispatching on identifier shape: an issue (`PRO-42`), a page (`PRO-DOC-3`), or a whole project (`PRO`). Issues and pages return their markdown.

A project returns the markdown of its issues and pages, one document each, a page of documents at a time. Every document opens with frontmatter naming its identifier. The first line gives the issue, page and document totals and which documents follow; when more remain, the last line gives the `offset` to call with next. A page stops early at 256 KiB of markdown, but always carries at least one document. No file paths are returned. To write a project to disk as files, use `lific export project` from the CLI.

| Name | Type | Required | Description |
| --- | --- | --- | --- |
| `identifier` | `string` | Yes | Issue ID (PRO-42), page ID (PRO-DOC-3), or bare project ID (PRO) |
| `offset` | `integer` | No | Project only: zero-indexed document offset |
| `limit` | `integer` | No | Project only: max documents per page (default 20, cap 100) |

### `create_issue`

Creates an issue in a project, or several at once.

| Name | Type | Required | Description |
| --- | --- | --- | --- |
| `project` | `string` | Yes | Project identifier (e.g. LIF) |
| `title` | `string` | Unless `issues` is given | Issue title |
| `description` | `string` | No | Markdown description |
| `status` | `string` | No | Status: backlog, todo, active, done, cancelled (default: backlog) |
| `priority` | `string` | No | Priority: urgent, high, medium, low, none (default: none) |
| `module` | `string` | No | Module name to assign to |
| `labels` | `string[]` | No | Label names to attach |
| `start_date` | `string` | No | Start date (ISO 8601 date, e.g. 2026-06-01) |
| `target_date` | `string` | No | Target/due date (ISO 8601 date, e.g. 2026-06-15) |
| `issues` | `object[]` | No | Create up to 50 issues in one call. Each item takes `title` (required) and the optional fields above except `project`. |

To file a burst of issues, pass `issues` instead of `title`. Only `project` may accompany it; the other top-level fields are rejected rather than merged into the items. The batch is one transaction: if any item is invalid (an unknown module, a bad status, a missing title), no issue is created and the error names the item, for example `Not found: issues[1]: module 'Nonexistent' not found in project`. The response lists every new identifier, one per line in item order. Unknown label names are ignored, as they are for a single issue.

After the confirmation line, the response lists up to three open issues in the same project that look like duplicates, one line each under `Similar open issues:`, so you can link or cancel one right away. In a batch the hint shrinks to identifiers on the item's own line, as in `- LIF-8: Title (similar open: LIF-3)`, and issues from the same batch are never listed as each other's duplicates. An issue qualifies when it shares at least two significant title words with the new issue (one, if the new title has only one), at least one of them in its own title. Common words such as "add", "fix" and "the" do not count. Done and cancelled issues are never listed, and the section is omitted when nothing qualifies.

### `update_issue`

Updates the provided fields of an issue.

| Name | Type | Required | Description |
| --- | --- | --- | --- |
| `identifier` | `string` | Yes | Issue identifier like PRO-42 |
| `title` | `string` | No | New title |
| `description` | `string` | No | New description (markdown) |
| `status` | `string` | No | New status: backlog, todo, active, done, cancelled |
| `priority` | `string` | No | New priority: urgent, high, medium, low, none |
| `module` | `string` | No | New module name. Omit to leave unchanged. Pass an empty string `""` to unassign the issue from its module. |
| `labels` | `string[]` | No | Replace labels |
| `start_date` | `string` | No | New start date (ISO 8601 date, e.g. 2026-06-01) |
| `target_date` | `string` | No | New target/due date (ISO 8601 date, e.g. 2026-06-15) |
| `evidence` | `string` | No | Completion evidence (markdown). Only accepted with `status: "done"` on an issue that is not already done. Saved as a verification comment. |

When a status change automatically completes or reopens linked plan steps, the response reports those step side effects.

Closing an issue whose description still has unchecked task items succeeds, and the response ends with a warning such as `Warning: 2 of 5 checklist items still unchecked.`

`evidence` records how the work was checked (test counts, the command that passed, what a person looked at) as a comment of kind `verification`, written in the same transaction as the close, and the response names the new comment. It is refused with any other status, including `cancelled`: cancelled work has nothing to verify. It is also refused on an issue that is already done, and when empty. A refusal changes nothing, including the other fields in the call. Closing without `evidence` behaves exactly as before. `get_issue` and `list_comments` print verification comments with a `[verification]` marker after the timestamp.

## Pages

### `get_page`

Gets a page and its content. A page of up to 30,000 characters is returned whole. A longer page returns its outline and the start of its content, with the call that reads one section at a time. The budget keeps a response under the roughly 50 KB at which agent harnesses cut tool output off.

| Name | Type | Required | Description |
| --- | --- | --- | --- |
| `identifier` | `string` | Yes | Page identifier like LIF-DOC-1 |
| `section` | `string` | No | Read one section: a heading's text (case-insensitive) or its anchor, such as `current-state`. The section runs from that heading to the next heading of the same or a higher level, so it includes its subsections. When several headings share the text, the response lists each one's anchor. An exact anchor wins over a text match. |
| `outline` | `boolean` | No | Return only the headings, each with its level and section size in characters, plus the page's `seq`. With `section`, outlines that section. |
| `since_seq` | `integer` | No | A `seq` from an earlier read. Returns only what changed in the content since then, as a unified diff with two lines of context, plus the current `seq`. Cannot be combined with `section` or `outline`. |

Lific keeps up to 50 recent versions of each page's content, dropping the oldest once they total 2,000,000 characters. When `since_seq` falls outside that history, the response says so and returns the page as a plain read would. Any `seq` works as the starting point, because seq values are shared by all issues, pages and comments on an instance.

Only ATX headings (`#` to `######`) count, and lines inside fenced code blocks are never headings. Anchors follow GitHub's rules: lowercase, punctuation dropped, spaces as hyphens, and `-1`, `-2` appended to repeats.

## Search and activity

### `get_briefing`

Summarizes a project for an agent resuming work, in one bounded read. Call it first at the start of a session instead of rebuilding the picture from search, pages, issue lists and plans.

| Name | Type | Required | Description |
| --- | --- | --- | --- |
| `project` | `string` | No | Project identifier (e.g. LIF). Optional when the session is bound to a repository. |
| `since` | `string` | No | ISO date or datetime. Adds a section for what changed strictly after it. Read like `get_activity`'s `since`: UTC unless an offset is given. |
| `pages` | `string[]` | No | Page identifiers to report on, such as the pages an `AGENTS.md` tells agents to read. At most 10. Without it, the three most recently updated pages are shown. |

The response opens with the current time and a `since` value to pass next time. The sections that follow are built from live records when the call is made. Nothing is stored or summarized by a model.

- **Since the cursor**, only when `since` is given: counts of issues created, issues closed, other status changes and pages edited, followed by the most recent of each. Status changes are net per issue, so an issue moved and moved back is not listed.
- **Active plans**, with progress and the next open step. The next step is the first unfinished step in tree order, descending into its first unfinished child.
- **Blocked** issues that are still open, each with the issues that block it and their status. A blocker in a project you cannot view is counted but not named.
- **Workable, not yet active** issues, highest priority first. Active issues are excluded here because they have their own section.
- **Key pages**: identifier, title, `seq`, size in characters, and whether the page changed since the cursor (or when it was last updated). Page bodies are never included. A page that does not exist and one you cannot view both read `not found`.
- **Active** issues, highest priority first.

Sections with nothing to report are left out. Issue sections show up to 8 items, plans up to 5, and each kind of change up to 5. The whole response stays under 6,000 characters. When a section is cut, either by its own limit or to fit that budget, it ends with the number of items left out and the call that lists them all.

Access follows `list_issues`: you need at least viewer access to the project.

### `search`

Searches issues, pages, and comments by text.

| Name | Type | Required | Description |
| --- | --- | --- | --- |
| `query` | `string` | Yes | Text to search for across issues, pages, and comments |
| `project` | `string` | No | Filter to a specific project (e.g. LIF) |
| `result_type` | `string` | No | Restrict results to one type: issue, page, or comment |
| `sort` | `string` | No | Sort mode: relevance (default, best match first) or recent (most recently updated first) |
| `mode` | `string` | No | Match mode: `fts` (default, tokenized full-text with prefix matching) or `literal` (case-insensitive substring, for punctuation-heavy needles like core:sodom, [RequiredSpecs], or --trace-plans that FTS tokenizes away). |
| `limit` | `integer` | No | Max results (default 20) |
| `offset` | `integer` | No | Zero-indexed offset for paging. Output appends a hint when more results exist. |

In `fts` mode every word is a required prefix term. When no result in the requested scope contains every word, the search runs again with any word allowed, ranks the hits by relevance (or recency, with `sort=recent`), and opens with `No result contains every word; showing partial matches ranked by relevance.` Paging walks the same partial list. A one-word query and `literal` mode never fall back.

### `get_activity`

Reads audit history for an issue, page, or project.

| Name | Type | Required | Description |
| --- | --- | --- | --- |
| `identifier` | `string` | Yes | What to read history for: an issue identifier (PRO-42), a page identifier (PRO-DOC-3 or DOC-3), or a bare project identifier (PRO) for the whole project's feed |
| `since` | `string` | No | Only entries strictly after this ISO date or datetime, returned oldest first. Omit it for the newest-first feed. |
| `limit` | `integer` | No | Max entries (default 30, cap 200) |
| `offset` | `integer` | No | Zero-indexed offset for paging. Output appends a hint when more entries exist. |

Audit timestamps are stored in UTC with one-second resolution, and `since` is read on the same clock. A bare date such as `2026-06-01` means midnight UTC. A datetime without an offset is UTC, and one with `Z` or an offset such as `-05:00` is converted to UTC. Fractional seconds are ignored. Entries in the same second as the cursor are excluded, so resuming from the timestamp of the last entry you read also skips anything else written in that second.

Writes made by a connected agent are attributed to that agent's own identity, not to the person who connected it, and each entry also records the transport the write came through (`mcp` for MCP requests, `web`, `api`, `cli`, or `system` for the others).

## Attachments

Uploads share the REST limits exactly: 10 MiB per file, and a magic-byte allowlist of PNG, JPEG, GIF, WebP, SVG, PDF, ZIP and plain text. The declared extension only decides the type for formats with no signature (`.svg`, `.txt`, `.log`, `.md`, `.csv`, `.json`); everything else is read from the bytes, so a renamed executable is rejected.

### `upload_attachment`

Uploads base64 file content and returns the attachment id plus a markdown snippet ready to embed (`![name](/api/attachments/12)` for images, `[name](/api/attachments/12)` otherwise). Pass at most one link target. An upload with no target stays unlinked and the orphan sweep collects it after 24 hours, so embed the snippet in an issue, page, or comment body before then.

| Name | Type | Required | Description |
| --- | --- | --- | --- |
| `filename` | `string` | Yes | File name, e.g. crash-log.txt or screenshot.png |
| `content_base64` | `string` | Yes | File bytes, base64 encoded (max 10 MiB decoded) |
| `entity` | `string` | No | Link the upload to this issue (LIF-42) or page (LIF-DOC-3, DOC-3 for workspace pages) |
| `comment_id` | `integer` | No | Link the upload to this comment id instead of an issue or page |

Linking to an issue or page requires Maintainer on its project, the same role editing it directly requires; linking to a comment requires Viewer. Uploading without a link target is open to any authenticated caller.

### `get_attachment`

Reads one attachment. Text is returned sliced by line with a header and a paging hint; PNG, JPEG, GIF and WebP come back as MCP image content a multimodal agent can look at; every other type returns a metadata summary and its download path rather than bytes.

| Name | Type | Required | Description |
| --- | --- | --- | --- |
| `attachment_id` | `integer` | Yes | Attachment id, e.g. 12 for /api/attachments/12 |
| `offset` | `integer` | No | Text only: zero-indexed first line to return |
| `limit` | `integer` | No | Text only: max lines to return (default 200, cap 500) |

Reading requires Viewer on any project the attachment is linked into. An attachment that is not linked anywhere yet has no project to gate on, so only its uploader or an admin can read it.

### `list_attachments`

Lists attachments on one entity, or across a whole project. Each row carries the id, filename, type, size, uploader, creation time, and the entities it is linked to. Links in projects the caller cannot see are omitted.

| Name | Type | Required | Description |
| --- | --- | --- | --- |
| `entity` | `string` | No | List attachments on this issue (LIF-42) or page (LIF-DOC-3, DOC-3 for workspace pages) |
| `project` | `string` | No | List every attachment in this project (e.g. LIF) instead |

Pass exactly one of `entity` or `project`. Either scope requires Viewer on the project involved.
