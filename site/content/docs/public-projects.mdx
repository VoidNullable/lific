---
title: Public projects
description: Publish a project so anyone can read it at its normal links without an account, while every change still needs a member's role.
---

Publishing a project makes it readable by everyone: visitors with no account, every signed-in account on the instance, and every API key and MCP connection. They read it at the project's normal links, the same ones members use. Changing anything still needs a role in the project. Publishing is off for every project until a lead turns it on, applies to one project at a time, and can be turned off again.

There is no separate public address. A link to an issue, page or plan in a published project works for anyone it is sent to:

```
https://your-instance.example/APP/issues/APP-42
https://your-instance.example/APP/pages/APP-DOC-3
https://your-instance.example/APP/plans/APP-PLAN-1
```

The links contain no secret. Search engines, scrapers and anyone who is sent one can read the project. If you want a specific group of people to read a project, add them as [project members](/docs/concepts/projects#members-and-roles) instead.

## Before you publish

- **Publishing exposes what is already there.** Every issue, page, plan, comment and attached file becomes readable, including those written long before, and so does the history of how they changed. Look through old descriptions, comments, edit history and files for internal hostnames, customer names, credentials and other private material first.
- **Secure the instance.** Set `auth.required = true` in the server configuration and turn off single-user mode (`web_auto_login`) before the server is reachable from the Internet. Publishing does not override either setting, and either one left open can give a visitor administrator access to everything, not only the published project. See [Authentication](/docs/self-hosting#authentication).
- **Unpublishing cannot recall anything.** Pages someone saved, files they downloaded and pages a crawler indexed stay out of your control.

## Who can publish

A project's lead or an instance administrator. A connected AI tool can publish only a project its owner could publish.

## Publish or unpublish a project

In the web UI:

1. Open the project's **Overview** and find **Public access**. Other members do not see this panel.
2. Read the list of what becomes readable, tick the box confirming you reviewed the content, and choose **Publish project**.
3. Copy the project link from the panel, or open it, and check it while signed out.

To unpublish, choose **Turn off public access** in the same panel. It takes effect on the next request and does not ask for confirmation. Readers without a role in the project then get the same answer as for a project that does not exist.

The CLI and MCP have no publication command. From a script, send `PUT /api/projects/{id}` with `{"is_public": true}` or `{"is_public": false}` as a lead or administrator. Every publish and unpublish is recorded in the project's activity log with the account that made the change.

Importing a [project archive](/docs/project-archives) always creates a private project, even if the source was published.

## What readers see

Anyone can read everything a project member with the Viewer role can read:

- Every issue, with its description, status, priority, module, labels, dates, assignees, waits and relations.
- Every page, with its content, status, folder and labels.
- Every plan and its steps.
- Every comment, with its author.
- The project's modules, labels and folders.
- Activity, edit history, insights and the board.
- Every file attached to the project, which anyone can download.
- Live updates, so an open page refreshes as members work.

Usernames and display names are part of that, because assignees, comment authors and activity name the people and agents behind them.

## What stays private

- Email addresses, passwords, API keys and session tokens, for every account.
- The project's member list, @mention suggestions, saved views and repository bindings, including the activity entries that record who joined, left or changed role and which repositories were bound.
- Project settings, and every instance setting.
- Exports and project archives, which still need a signed-in account (exports) or the lead role (archives).
- Deleted items in the trash.
- Workspace pages, and every project that is not published. A plan step or relation that points into a private project shows no identifier or status for it. Activity leaves out what a private project recorded about the published one (a private plan step linked to a published issue, for example), and a relation or move involving a private issue shows "a private issue" in its place.

## Reading without an account

A signed-out visitor who opens a project link reads the project directly, with no sign-in step. Where a member would see an edit control, the visitor sees a **Sign in** button instead. Signing in keeps them on the same page; if their account has a role in the project, the edit controls appear.

Opening the instance's home address while signed out:

- with one published project, opens that project's overview;
- with several, lists them;
- with none, shows the sign-in page.

A link into a project that is not published shows the sign-in page, and the API answers exactly as it does for a project that does not exist.

Markdown is rendered more strictly for signed-out readers than for members. Images load only when they point at this instance's attachments; any other image shows its alt text. Elements that load content on their own (video, audio, frames, embedded objects, stylesheets, SVG and forms) are removed. Ordinary links remain, because the reader chooses whether to follow them.

## Signed-in accounts and API keys

An account or key with no role in a published project reads it like any visitor, through the ordinary REST API and MCP tools, and gets `403` for every change. The project appears in its project list and sidebar. Its own views, such as home, the inbox and briefings, still cover only projects it is a member of, so publishing a project does not fill strangers' dashboards with its work.

## Limits

Requests with no credential share limits so they cannot crowd out signed-in users. Signed-in reads are not affected.

| Limit | Value | When exceeded |
| --- | --- | --- |
| Reads per client IP | 600 per minute | `429` with `Retry-After` |
| Anonymous requests in progress, whole instance | 4 | `503` with `Retry-After` |
| Anonymous file downloads in progress, whole instance | 4 | `503` with `Retry-After` |
| Thumbnails or previews being generated for anonymous readers | 1 at a time | `503` with `Retry-After` |
| Largest file a thumbnail or preview is generated from for an anonymous reader | 32 MiB | `404` for the thumbnail or preview; the file still downloads |
| Live-update connections from anonymous readers, whole instance | 64 | `429` |

A thumbnail that already exists, for example because a signed-in user viewed the file, is served whatever the file's size.

An anonymous download that stalls for 15 seconds, or runs for 5 minutes, is ended with an error rather than a clean finish. If you run Lific behind a reverse proxy, list it in `server.trusted_proxies` so each visitor is counted separately; otherwise every visitor shares the proxy's one bucket. See [Client addresses behind a proxy](/docs/self-hosting#client-addresses-behind-a-proxy). Set bandwidth and connection limits on the proxy too, because slow readers can still hold network connections open.

Every response to a request with no credential carries `Cache-Control: no-store`, `nosniff`, `Referrer-Policy: no-referrer`, `X-Frame-Options: DENY` and `Cross-Origin-Resource-Policy: same-origin`, so nothing outlives an unpublish in a shared cache. Anonymous downloads also carry `Content-Security-Policy: default-src 'none'; sandbox`; anything other than a plain image or media file downloads rather than opening in the browser, and SVG files are served as `application/octet-stream`.

[Reading without a credential](/docs/rest-api/public) lists the API routes a visitor can use.

## Upgrading from 2.x

Lific 2.x served published projects on a separate, reduced view under `/public/APP` and `/public/api/projects/APP`. Lific 3.0 removes both. Old `/public/APP/...` links redirect to the same place under `/APP/...`, and `/public/api/...` answers `404`. What a published project shows has also grown: plans, edit history, assignees and waits are now readable. See [Upgrading](/docs/upgrading#v30) before you upgrade an instance with a published project.

Publication is a per-project setting stored in the database. It defaults to off, and upgrading publishes nothing.
