A project holds everything else and is the unit of access. The [projects concept page](/docs/concepts/projects) explains identifiers, roles and what deletion destroys. The project's own issues, pages and plans are on [Issues, pages and plans](/docs/rest-api/work); its repository bindings are on [Repositories and commits](/docs/rest-api/repositories).

## Projects

### GET `/api/projects`

The projects you can read, as a `Project` array in your own sidebar order. A project you are not a member of is absent rather than an error. Administrators see every project.

### POST `/api/projects`

Creates a project. Any signed-in caller.

Body: `name`, `identifier`, and optional `description` (Markdown, default empty), `emoji`, `lead_user_id` and `conventions`: the template the project's [conventions page](/docs/concepts/pages#conventions-page) starts from, `empty` (default), `ai_managed`, `human_managed` or `human_owned`. The project starts with that page. The identifier is one to five characters, an uppercase letter followed by uppercase letters or digits, and cannot be `DOC`; anything else is `400`. An identifier another project already uses, compared without regard to case, is `409` naming it.

The lead gets a `lead` membership. Leaving `lead_user_id` out, or naming yourself, makes you the lead with no further check; for a connected tool, "yourself" is the person who owns it. Naming **somebody else** gives them lasting access, so it needs a [recent browser session](/docs/rest-api#which-credentials-an-endpoint-accepts).

Returns the `Project`.

```bash
curl -X POST "$LIFIC/api/projects" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"name":"Mobile app","identifier":"APP","emoji":"lucide:Smartphone"}'
```

### GET `/api/projects/{id}`

One `Project`. **Viewer.**

### PUT `/api/projects/{id}`

Changes project settings. **Lead.** Every field is optional: `name`, `identifier`, `description`, `emoji` (null clears it), `lead_user_id` (null clears it) and `is_public`.

Setting `lead_user_id` to a user also gives them a `lead` membership, so that one change needs a recent browser session. Clearing it does not.

`is_public: true` makes the project readable by everyone through the ordinary routes, [with or without a credential](/docs/rest-api/public), and `false` withdraws that on the next request. See [Public projects](/docs/public-projects) before turning it on: it exposes existing content, not just what you write afterwards.

Changing the identifier renames every issue, page and plan identifier in the project at once; old written references stop resolving. The new identifier follows the rules for creating one, and one already used by another project is `409`. Returns the `Project`.

### DELETE `/api/projects/{id}`

Deletes the project and everything in it, immediately and permanently, including anything in its trash. **Lead.** The check is repeated inside the delete transaction. Returns `{"deleted": true}`.

### POST `/api/projects/{id}/archive`

Takes the project out of the instance and keeps it as one compressed file in the data directory. Same permission as deleting: **Lead**, checked again inside the transaction. Returns `201` with the `ArchivedProject` below. See [Archiving projects](/docs/archiving-projects).

### GET `/api/archived-projects`

Every archived project, newest first. **Administrator** only. Each entry has `id`, `identifier`, `name`, `description`, `emoji`, `file_name`, `size_bytes`, `issue_count`, `page_count`, `archived_at`, `archived_by`, `archived_by_name`, `was_public`, and `file_present`, which is `false` when the file is no longer on disk.

### POST `/api/archived-projects/{id}/unarchive`

Brings the project back from its file. **Administrator** only. Returns `{"project_id", "identifier", "was_public"}`. `409` when a live project already has the identifier or the file no longer matches its recorded checksum, `404` when the file is missing, `429` while another archive operation is running.

### PUT `/api/projects/reorder`

Sets your own sidebar order. Other people's order is unaffected. Body: `ids`, the project ids in the order you want. Ids you leave out keep their relative order after the ones you list. A duplicate or an id you cannot see is `400`. Returns the reordered `Project` array.

## Sidebar folders

Folders (the routes still say groups) are private to the person who made them. Every route here works only on your own folders; another person's folder answers `404`. Filing a project in a folder changes nothing about the project.

Folders nest up to four levels deep, and each level orders its folders and projects together. A folder has `id`, `user_id`, `name`, `parent_id` (null at the top level), `depth` (1 at the top level), `sort_order`, `items`, `project_ids`, `created_at` and `updated_at`. `items` lists what the folder holds in order, each as `{"kind": "folder", "id": 3}` or `{"kind": "project", "id": 7}`; `project_ids` lists just the projects. Both leave out projects you can no longer read, so a project you lose access to drops out of the folder without being unfiled.

Folder names are unique across all your folders, not just within one. A name you already use is `409`. Names are at most 80 characters, and you can have at most 200 folders.

### GET `/api/project-groups`

Your folders, depth-first.

### GET `/api/project-groups/layout`

Your whole sidebar tree: `root` (the top level, as items), `groups` (every folder, depth-first) and `max_depth`.

### POST `/api/project-groups`

Creates a folder after the folders already at its level. Body: `name`, optional `parent_id`, and optional `contains`, an item to move into the new folder in the same write. Creating past the depth limit, or a `contains` move that is refused, is `400` and creates nothing. Returns the folder.

### PUT `/api/project-groups/move`

Moves a project or folder. Body: `item`, `parent_id` (null or absent for the top level) and optional `before`, an item already in that folder to place it in front of; without it the item goes last. Moving a folder into itself or one of its subfolders, past four levels, or before an item that is not in the target folder is `400` with a message that says why, and changes nothing. Moving a project you cannot read is `403`. Returns the layout.

### PATCH `/api/project-groups/{id}`

Renames a folder. Body: `name`. Returns the folder.

### DELETE `/api/project-groups/{id}`

Deletes a folder. What it held moves to its parent, in its place. No project is deleted. Returns `{"deleted": true}`.

### PUT `/api/project-groups/assign`

Moves a project to the end of one of your folders, or to the end of the top level. Body: `project_id` and `group_id` (null for the top level). A project sits in at most one of your folders. Filing a project you cannot read is `403`. Returns `{"ok": true}`.

### PUT `/api/project-groups/reorder`

Sets the order of folders among their siblings. Body: `ids`, folder ids in the order you want; within each level, listed folders take the folder positions first and the rest follow in their current order. Projects stay where they are. Returns your folders.

## Members and roles

The role rules are in [Roles](/docs/rest-api#roles). A member record has `project_id`, `user_id`, `role` and `created_at`.

### GET `/api/projects/{id}/members`

Members with their names: each record adds `username` and `display_name`. **Viewer.**

### POST `/api/projects/{id}/members`

Adds a member. **Lead, from a recent browser session**, even for a caller who is a lead: an API key cannot hand out standing access. Both checks run inside the transaction that writes the row.

Body: `user_id` and optional `role` (`viewer`, `maintainer` or `lead`; default `viewer`). An unknown role is `400`, an unknown `user_id` is `404`, and a user who is already a member is `409`. Returns the member record.

```bash
curl -X POST "$LIFIC/api/projects/1/members" \
  -H "Authorization: Bearer $SESSION_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"user_id":2,"role":"maintainer"}'
```

### PATCH `/api/projects/{id}/members/{user_id}`

Changes a member's role. **Lead.** Body: `role`. Raising a role needs a recent browser session; lowering it, or setting the role it already has, does not, so an API key can still reduce access during an incident. Demoting the last `lead` is `409`. Returns the member record.

### DELETE `/api/projects/{id}/members/{user_id}`

Removes a member. **Lead**, with no recency requirement. Removing the last `lead` is `409`; promote somebody first. If the removed member was the primary lead, `lead_user_id` moves to another lead or is cleared. Returns `{"deleted": true}`.

### GET `/api/projects/{id}/my-role`

Your own standing, so a client can decide what to show without reading the roster. **Viewer**, or anyone who can read a published project, so a reader with no role gets `{"role": null, "is_admin": false}` instead of `403`. Returns `role` (`viewer`, `maintainer`, `lead`, or null when you are not a member) and `is_admin`. For a connected tool, the role is its owner's.

## Saved views

Saved views are personal. Every route lists and changes only your own views in one project, and needs a signed-in caller. **Viewer.**

A view has `id`, `project_id`, `user_id`, `name`, `config`, `is_default`, `created_at` and `updated_at`.

`config` is a string containing JSON, at most 8 KiB. Lific checks only that it parses and never reads inside it. The web UI stores this shape and tolerates missing fields. Each filter is a list of values; views saved by older versions, with one string per filter, still load:

```json
{
  "version": 1,
  "layout": "list",
  "filterStatus": ["active", "todo"],
  "filterPriority": [],
  "filterLabel": [],
  "filterModule": [],
  "filterAssignee": [],
  "searchQuery": "",
  "sortField": "updated",
  "sortDir": "desc",
  "groupBy": "status",
  "density": "comfortable",
  "laneBy": "status",
  "hiddenStatuses": []
}
```

### GET `/api/projects/{id}/views`

Your views in the project.

### POST `/api/projects/{id}/views`

Creates a view. Body: `name`, `config` and optional `is_default`. Returns the view.

### PATCH `/api/projects/{id}/views/{view_id}`

Changes any of `name`, `config` and `is_default`. Returns the view.

### DELETE `/api/projects/{id}/views/{view_id}`

Deletes the view. Returns `{"deleted": true}`.

## Board and numbers

### GET `/api/projects/{id}/board`

The project's issues grouped into columns. **Viewer.** Query: `group_by`, which is `status` (the default), `priority` or `module`. Returns an object whose keys are column names (a status, a priority, or a module name with `unassigned` for issues without one) and whose values are `Issue` arrays. Empty columns are left out. The board reads at most 500 issues.

### GET `/api/projects/{id}/issue-counts`

Issue counts by status: `backlog`, `todo`, `active`, `done`, `cancelled` and `total`. **Viewer.** Issues in the trash are not counted.

### GET `/api/projects/{id}/insights`

Charts for the project's insights tab. **Viewer.** Query: `weeks` (default 12, clamped to 1 through 52).

Returns:

- `weeks`
- `created_per_week` and `closed_per_week`: arrays of `week_start` and `count`
- `status_counts`: the issue-count object above
- `priority_counts`: `urgent`, `high`, `medium`, `low`, `none` and `total`
- `module_counts`: `module_id` (null for no module), `name` and `count`
- `top_actors`: the actor summary described under [project activity](#get-apiprojectsidactivityactors)

### GET `/api/projects/{id}/mention-candidates`

People who can be `@`-mentioned in the project's comments: `user_id`, `username` and `display_name`. **Viewer.** Only people who can see the project: its members and the instance administrators.

## Activity

The activity log records who changed what, through which interface. The per-issue, per-page and per-plan feeds are on [Issues, pages and plans](/docs/rest-api/work#activity).

### GET `/api/projects/{id}/activity`

The project's activity, newest first. **Viewer.** Query: `limit` (default 50, at most 200) and `offset`.

Returns `items` and `has_more`. Each item has:

- `id`, `ts`
- `actor_user_id`, `actor_username`, `actor_display_name` (null once the account is gone) and `actor_is_bot`
- `transport`: `web`, `mcp`, `api`, `cli` or `system`
- `entity_type`, `entity_id`, `entity_label`, and `project_id`, `issue_id`, `page_id` where they apply
- `action`: such as `create`, `update`, `delete`, `attach`, `detach`, `link` or `unlink`
- `field`, `old_value` and `new_value` for a field change. A page content edit has `field` set to `content_diff`, `old_value` null and `new_value` holding a unified diff of the change (hunks with three lines of context, no file header) instead of both full bodies. Entries written before this format, or by a direct database update, carry `field: "content"` with the full old and new content.

### GET `/api/projects/{id}/activity/actors`

Totals per actor in the project. **Viewer.** Each entry has `actor_user_id`, `username`, `display_name`, `is_bot`, `actions`, `last_ts` and `top_transport` (the interface they used most).

### GET `/api/agents/activity`

What connected tools have been doing, across every project you can see; the web UI's Agent activity page draws it. Any signed-in caller. Only bot accounts count as agents, and only actions in projects you can see are counted. An agent's MCP reads count as well as its writes; reads are kept for 30 days.

Query: `window` (`1h`, the default, `24h` or `7d`; anything else is `400`) and `tz`, your offset from UTC in minutes east (default 0), which aligns the buckets to your local clock.

Each action is one of four kinds: `read`, `edit`, `create` (of an issue, page, plan, module, project, label or folder) or `close` (an issue moved to `done` or `cancelled`). A count object has `read`, `edit`, `create` and `close`. Returns:

- `window`, `now` (server time, RFC 3339 UTC) and `bucket_seconds` (300, 3,600 or 86,400)
- `buckets`: 12, 24 or 7 of them, oldest first, each `start` (RFC 3339 UTC) plus the four counts
- `totals`: the counts for the whole window
- `agents`: every agent that acted in the last 30 days, each with `user_id`, `username`, `display_name`, `tool_id` (such as `opencode`), `owner` (`user_id`, `username`, `display_name`), `status` (`active` when it last acted under 10 minutes ago, `idle` under an hour, otherwise `inactive`), `last_seen`, `counts` and `series` (its total actions per bucket)
- `active_count`: how many agents are `active`
- `recent`: the latest actions, newest first, at most 30, each with `at`, `kind`, `agent` (`user_id`, `display_name`), `entity_type`, `identifier`, `title`, `detail`, `route` (the web UI path, or null when the item is gone) and `tool` (the MCP tool, for reads)

### GET `/api/home/overview`

The numbers behind the web UI's Home page and a project's overview, across every project you can see. Any signed-in caller.

Query, every field optional: `since` (an ISO 8601 instant; anything else is `400`), `tz` (your offset from UTC in minutes east, default 0, which decides where each day starts) and `project_id`, which narrows every number to that project. A project you cannot see counts as empty rather than an error.

Returns:

- `open_total`: open issues (not `done` or `cancelled`)
- `age_buckets`: open issues by age, youngest first, with `key` (`week`, `month`, `quarter`, `half` or `older`), `total`, a count per priority (`urgent`, `high`, `medium`, `low`, `none`), `agent_ready` (unassigned, unblocked, not active and not claimed) and `needs_human`
- `open_trend`: `date` and `count` of open issues at the end of each of the last 91 days, ending today
- `projects`: `project_id`, `open` and `last_activity` for each project with open issues or any activity
- `since`: `agents_opened`, `agents_closed`, `people_opened` and `people_closed` after `since`, or null without it
- `my_done`: `date` and `count` of issues you or your connected tools moved to `done`, for each of the last 84 days, ending today
- `claims`: open issues under a live claim, most recently claimed first, each with `issue_id`, `project_id`, `identifier`, `title`, `status`, `priority` and `claim`

## GitHub import

### POST `/api/projects/{id}/import/github`

Copies a GitHub repository's issues and their comments and labels into the project, or previews what would be copied. **Lead.** The request body may be at most 16 KiB.

Body:

| Field | Default | Meaning |
| --- | --- | --- |
| `repo` | required | `owner/name`. |
| `token` | none | A GitHub token, needed for private repositories and higher rate limits. It is used for this request only and not stored. |
| `state` | `all` | Which GitHub issues to read: `open`, `closed` or `all`. |
| `map_open` | `backlog` | Lific status for open GitHub issues. |
| `map_closed` | `done` | Lific status for closed GitHub issues. |
| `dry_run` | `false` | Count what would be created and write nothing. |

Each imported issue records its origin in `source` (such as `github:owner/name#12`), so running the import again skips issues it already brought in.

Returns `dry_run`, `issues_created`, `issues_skipped_existing`, `comments_created`, `labels_created`, `comments_planned`, `labels_planned`, `skipped_non_issues` (pull requests), `skipped_assignees` and `skipped_other`.

One import runs per project at a time and four across the instance; another request meanwhile is `409`. A repository past Lific's import limits is `413`, with the limit named.
